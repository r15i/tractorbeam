## Context

See `proposal.md` - Why. Relevant state from the altitude-channel experiment and fresh source reading done for this proposal:

- `RESCUE_FLYAWAY` (`gps_rescue_multirotor.c`) only evaluates inside `case RESCUE_FLY_HOME:`, comparing `velocityToHomeCmS` (derived from consecutive `distanceToHomeCm` samples) against `0.2 * targetVelocityCmS`, accumulating over a 20s failing-window - structurally the same shape as the altitude channel's `RESCUE_ATTAIN_ALT` check, just on distance instead of altitude.
- Reaching `RESCUE_FLY_HOME` requires passing, in order: `RESCUE_INITIALIZE` → `RESCUE_ATTAIN_ALT` → (`RESCUE_PITCH_FORWARD` or `RESCUE_ROTATE`, depending on `rescueState.sensor.isHeadingOK`) → `RESCUE_FLY_HOME`. The altitude experiment already confirms how to clear `ATTAIN_ALT` (feed a climb rate that crosses the return-altitude gap before the 10s failing-window closes).
- **New finding, confirmed by reading `imu.c` directly**: this SITL build resolves `ENABLE_SIMULATOR && !defined(USE_IMU_CALC)` to false for `imu.c`'s translation unit (macro is defined twice across `common_post.h` and the simulator's `platform.h`, with `common_post.h`'s `0` apparently winning for this file) - so it compiles the *real* heading-confidence path (`updateGpsHeadingUsable()`), not the simulator's `canUseGPSHeading = true` shortcut. Empirically confirmed too: our altitude runs landed in `RESCUE_PITCH_FORWARD`, not `RESCUE_ROTATE`, after `ATTAIN_ALT` cleared - meaning `isHeadingOK` was false at that point, consistent with the real path being active.
- `gpsHeadingConfidence` only rises when `imuCalcGroundspeedGain()` is nonzero, and that function multiplies in a `pitchSuppression` term that is **exactly zero at level pitch** (`attitude.values.pitch == 0`) - our `FdmState`'s fixed level orientation quaternion (`sitl_transport.py`'s `LEVEL_ORIENTATION_QUAT`) guarantees this gain stays zero forever, regardless of velocity fed. `RESCUE_PITCH_FORWARD` gives up after 15s and falls back to `rescueEmergDescent()` if heading never validates.
- `FdmState.velocity_enu` is currently always `[0, 0, 0]` (see `sitl_transport.py`) - SITL's `gpsSol.groundSpeed`/course-over-ground come from this field directly (`sitl.c`'s `setVirtualGPS()`), not from differentiating consecutive lat/lon fixes. A spoof that only rewrites `state.lat`/`state.lon` each tick, as the altitude and prior full-loop experiments did, reports zero GPS speed no matter how fast the position actually changes.

## Goals / Non-Goals

**Goals:**
- Reach `RESCUE_FLY_HOME` reliably in the SITL harness, using only synthetic (directly-injected) sensor data - no real closed-loop flight dynamics.
- Test the same accept/reject framing as the altitude channel (frozen / naive-jump / adaptive) against `RESCUE_FLYAWAY`, plus the specific case the user asked for: adaptive convergence to a position other than true home.
- Keep the two required correlated signals (forward pitch angle, matching `velocity_enu`) as an explicit, minimal addition - not a general flight-dynamics model.

**Non-Goals:**
- Not modeling real aerodynamics, motor response, or a closed loop between commanded motor output and reported attitude/velocity - the pitch angle and velocity are directly authored per profile, matching how the altitude experiment authored altitude directly.
- Not attempting the `ENABLE_RESCUE_PLAN=1` (flight-plan autopilot) code path - this change targets the same forced `ENABLE_RESCUE_PLAN=0` classic-controller build already established.
- Not re-testing the altitude channel itself; it's a precondition this change clears using the already-confirmed adaptive rate, not a fresh variable.

## Decisions

**Decision 1: Feed a synthetic forward-pitch + matching velocity pair, not just a moving lat/lon**
- *Rationale*: `imuCalcGroundspeedGain()` requires both GPS-reported groundspeed above ~1 m/s *and* nonzero forward pitch to produce confidence; a level attitude zeroes the gain outright regardless of velocity. This is a second instance of the project's own established principle (`docs/Extended_Kalman_Filter_Bypass.md`: correlated fake signals across channels evade checks; contradictory ones don't) - here applied to GPS-heading validation instead of accelerometer/EKF innovation.
- *Alternatives considered*: Try to trigger `RESCUE_ROTATE` directly by other means (e.g., a debug/CLI override of `isHeadingOK`). Rejected - no such override exists in this Betaflight version (confirmed: `canUseGPSHeading` is a static-linkage internal, not exposed via CLI/MSP), and directly poking firmware internals would stop this being a sensor-level spoofing test.

**Decision 1 addendum, found while implementing: pitch alone doesn't stick - the accelerometer has to agree**
- *What happened*: sending only the pitched orientation quaternion left `MSP_ATTITUDE` reporting `pitch=0` no matter how long the run continued. Traced to `imuUpdateAttitude()` (`imu.c`): it unconditionally calls the real attitude filter, `imuMahonyAHRSupdate()`, every scheduler tick, from gyro + accelerometer - it does not read or trust an injected quaternion at all. That filter's accelerometer-correction term is a cross product between the measured (fed) acceleration vector and `rMat.m[NWU_U]` ("earth-up expressed in the body frame," the filter's own current pitch/roll estimate); feeding a level accelerometer (`[0, 0, -GRAVITY]`, unchanged) tells the filter every cycle "this body is level," overriding the injected quaternion within one update.
- *Fix*: `sitl_transport.py` gained `pitch_tilted_accel(pitch_deg)`, derived from - and numerically verified against - this exact codebase's `rMat.m[NWU_U]` formula (not generic rotation math): for the pitch quaternion used here, `rMat.m[NWU_U] = (-sin(theta), 0, cos(theta))`, translated through `sitl.c`'s negate-before-send convention to `linear_acceleration_xyz = [GRAVITY*sin(theta), 0, -GRAVITY*cos(theta)]`. `FdmState.pack()` now derives both the quaternion and this accelerometer tilt from the same `pitch_deg`, so they can't drift out of sync the way the first attempt did. Confirmed empirically: `MSP_ATTITUDE` converges to the fed pitch within ~1s and holds it (previously stuck at 0 indefinitely).
- *Why this matters beyond fixing the bug*: it's a third, independent confirmation of the project's core finding, this time against the real attitude filter rather than a heuristic rescue check - a single spoofed channel (here, orientation) gets corrected away by whichever other sensor the filter actually trusts (accelerometer), unless that channel is *also* spoofed consistently. Worth keeping as a result in the paper, not just an implementation footnote.

**Decision 2: Compute the pitched-forward orientation quaternion and its matching accelerometer tilt analytically, reusing the Gazebo-bridge conjugation solved in `sitl_transport.py`**
- *Rationale*: `sitl_transport.py` already derived the raw quaternion to send for a *level* attitude, by solving the `ENABLE_GAZEBO_BRIDGE` conjugation algebraically. The same derivation, parameterized by a target pitch angle (and, if needed, yaw matching the direction of travel), extends directly rather than needing new machinery - and, per the addendum above, the accelerometer tilt is derived from the same `rMat.m[NWU_U]` row the pitch quaternion produces, so both signals originate from one parameter (`pitch_deg`) instead of two independently-set fields that could contradict each other.
- *Alternatives considered*: Send Euler angles instead of a quaternion. Not available - `fdm_packet`'s `imu_orientation_quat` field is quaternion-only (see `target.h`); conversion still has to happen somewhere, so doing it once analytically in `sitl_transport.py` is no more work and keeps one source of truth.

**Decision 3: Reuse the altitude experiment's profile structure (frozen / naive-jump / adaptive), applied to distance-to-home**
- *Rationale*: Same accept/reject framing, same statistical shape (rate-based checks with a fixed failing-window), so reusing the structure keeps the two channels' results directly comparable in the paper - which is the point of testing both.
- *Alternatives considered*: A continuous rate sweep (as started for altitude's "partial" profile) instead of three discrete points. Deferred to a follow-up if time allows; the three-point structure already demonstrated the key contrast for altitude and keeps this change's scope bounded.

## Risks / Trade-offs

- **[Risk]** The exact pitch angle / velocity magnitude needed to clear the 1.5 confidence threshold within a reasonable test window is not yet empirically known (the formula has a 2s integration time constant and several multiplicative suppression terms - roll, yaw-rate, pitch - each of which must individually be non-suppressing). **[Mitigation]** Task list includes an isolated "heading-confidence-only" probe step (arm, rescue, feed pitch+velocity, watch `DEBUG_ATTITUDE` slot 1 for `gpsHeadingConfidence*100`) before attempting the full horizontal-spoof profiles, so this is characterized empirically rather than guessed, mirroring how the altitude gate's exact threshold was found.
- **[Risk]** `RESCUE_PITCH_FORWARD` has its own 15s timeout independent of the heading-confidence time constant; if clearing confidence takes longer than 15s the phase falls back to `rescueEmergDescent()` before ever reaching `ROTATE`/`FLY_HOME`. **[Mitigation]** The probe step above measures actual time-to-confidence before committing to the full profile set; if it's close to 15s, feed a stronger (still physically-labeled) pitch/velocity pair rather than tuning against the wall.
- **[Trade-off]** Feeding a synthetic pitch angle is one step closer to a real flight-dynamics model than the altitude experiment needed. Accepted because it's still a fixed, directly-authored value per profile (not a closed loop reacting to motor output), keeping scope bounded per the Non-Goals above.
